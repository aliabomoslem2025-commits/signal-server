# Local device-auth deployment

The `feature/local-lan-auth` branch adds a local device-authentication endpoint to the Signal server. It uses a dedicated DynamoDB-compatible table and verifies device signatures with an administrator-preauthorized EC P-256 public key.

## 1. Create the local-auth table

For DynamoDB Local:

```sh
export DYNAMODB_ENDPOINT=http://127.0.0.1:8000
export AWS_ACCESS_KEY_ID=dummy
export AWS_SECRET_ACCESS_KEY=dummy
export AWS_REGION=us-east-1
./deploy/local-auth/create-table.sh
```

The script is idempotent and enables TTL on the `expiresAt` attribute for short-lived challenges and registration sessions.

## 2. Configure the server

Set these variables on the Signal server process:

```sh
LOCAL_AUTH_TABLE=signal_local_device_auth
LOCAL_AUTH_ADMIN_TOKEN=<high-entropy-secret>
```

Generate a token with `openssl rand -base64 48`. Keep it in the server's secret manager or environment, never in the APK or static dashboard files.

## 3. Configure TLS and LAN routing

The app uses HTTPS and the Signal service trust store. The server certificate must chain to a CA trusted by the app's configured trust store. Installing a CA in Android's general user trust store alone may not be sufficient because the Signal service client uses its own trust store.

Expose the server API only on the management LAN/VPN. Restrict `/v1/local-auth/admin/*` at the network firewall or reverse proxy as an additional control.

## 4. Provision devices

Each device binding contains:
- E.164 phone number;
- `Settings.Secure.ANDROID_ID`;
- Base64 X.509 EC P-256 public key generated by the app's Android Keystore key manager;
- optional display name.

The private key must never leave Android Keystore. The current dashboard accepts the public key manually. The current app branch does not yet expose a dedicated enrollment/export screen, so administrators need a trusted provisioning path to obtain the public key before enabling a device.

## 5. Authentication flow implemented in this branch

1. The app sends phone number and Android ID to `POST /v1/local-auth/challenge`.
2. The server checks the administrator-created device binding and returns a nonce.
3. The app signs the nonce with its Android Keystore private key.
4. The app sends the signature to `POST /v1/local-auth/verify`.
5. The server verifies the signature and returns a six-digit compatibility code plus a short-lived registration session ID over HTTPS.
6. The app places the code into the existing verification-code UI and submits it to `POST /v1/local-auth/submit-code`.
7. `PhoneVerificationTokenManager` accepts the registration session only after that code has been verified.

The code returned in the HTTPS response is not a second factor. Device possession is established by the Keystore signature; the code preserves compatibility with Signal's existing registration UI and session contract.

## 6. Important deployment boundary

This branch is an implementation draft, not a verified all-local production deployment.

The Signal server still contains and initializes the upstream registration-service/SMS/voice path. FCM/APNs, storage/CDN, and calling dependencies have not been replaced by LAN-only equivalents. The Android app still contains SMS-related code/dependencies, the server-config asset is not yet manageable through an in-app settings screen, and a separate app-specific PIN has not been implemented. The complete app/server build and end-to-end LAN test suite has not been run.

Do not treat the system as fully operational or fully offline until those items are completed and verified.
